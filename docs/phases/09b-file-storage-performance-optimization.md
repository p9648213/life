# Phase 09B: File-Storage Performance Optimization (Deferred)

Goal: improve one measured file-storage bottleneck while preserving the Phase 09A format, correctness, limits, and durability guarantees.

This is an optional, repeatable optimization phase. It does not block Phase 10. Enter it after [Phase 23: Benchmarking and Profiling](23-benchmarking-profiling.md), or earlier only when a reproducible storage benchmark already demonstrates a concrete problem.

## Expected Behavior

The chosen workload shows a meaningful measured improvement without changing application-visible storage behavior. Existing valid data remains readable, or a versioned migration is provided. Malformed and adversarial input remains bounded and explicit.

Optimize one diagnosed cost at a time. Possible targets include allocation, peak memory, lookup time, mutation time, startup time, or file growth. Do not implement every technique as part of this phase.

Codec boilerplate may also be reduced here after several record types have been implemented manually. A declarative macro is a maintainability improvement, not a runtime performance optimization, and does not by itself satisfy this phase's performance checkpoint.

## Candidate Directions

- reuse record scratch buffers instead of allocating one buffer per record;
- calculate or estimate encoded size to reserve bounded capacity;
- encode through a buffered writer instead of holding a complete encoded file in memory;
- stream snapshot replacement one record at a time to reduce peak memory;
- build a bounded in-memory ID-to-offset index for measured lookup costs;
- introduce a snapshot plus append-only mutation log when rewrite cost is proven dominant;
- compact a log under an explicit size or ratio policy;
- add a new file-format version when the optimized representation is incompatible.
- generate repetitive record `Encode` and `Decode` implementations with a declarative macro after the stable manual pattern is understood.

Memory mapping, borrowed decoded records, pages, and unsafe code require separate justification. They are not default extensions of Phase 09A.

## Requirements

- Record the benchmark, data shape, configured limits, and baseline result before changing the design.
- State the bottleneck hypothesis and which storage layer owns it.
- Preserve the typed record boundary so macro-generated codecs do not determine the persistence strategy.
- If a codec macro is added, require its invocation to state persistent field order and generate the existing manual codec contract without runtime dispatch or hidden file I/O.
- Keep macro-generated bytes compatible with the documented format unless a deliberate versioned migration is introduced.
- Keep full scans linear and examine every permitted input byte only a bounded number of times.
- Measure both time and peak memory when the change trades one for the other.
- Preserve or deliberately version the persistent format.
- Preserve explicit errors for malformed, oversized, truncated, and unsupported data.
- Preserve the rule that failed persistence cannot be reported as success.
- Document crash recovery, compaction, and partial-write behavior if an append-only log is introduced.
- Bound index size, log growth, temporary space, and recovery work under configured limits.
- Compare the optimized result with the same workload and environment used for the baseline.
- Remove the optimization if the result is noise or the added complexity is not justified by the measured gain.

## Tests and Measurements

- all Phase 09A behavior tests still pass;
- old-format fixtures remain readable, or migration and unsupported-version behavior are tested;
- optimized and baseline implementations produce equivalent logical records;
- macro-generated codecs, if added, produce the same documented bytes and errors as their manual equivalents;
- maximum-size reads and mutations stay within the documented time and memory scaling;
- buffer reuse or streaming tests show bounded allocation or working memory where practical;
- indexes rebuild correctly after reopening and never return stale locations;
- append-only recovery rejects or deliberately handles a truncated final entry;
- compaction preserves exact live records and stable IDs;
- failed optimized writes, flushes, renames, or compactions are not reported as success;
- benchmark results include enough repeated samples to distinguish improvement from noise.

## Checkpoint

You are done with one pass through this phase when a reproducible benchmark demonstrates the original bottleneck, the smallest targeted change improves it meaningfully, correctness and adversarial limits remain intact, and the new complexity and recovery behavior are documented.

Return to this phase only for another measured bottleneck. Continue the main roadmap independently from [Phase 10: Static Files and CSS](10-static-files-css.md).
